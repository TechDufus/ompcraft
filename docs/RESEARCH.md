# ompcraft research

Status: research only, no implementation. Compiled 2026-11-09.

ompcraft is a World of Warcraft: Forever addon plus a companion app on the gaming PC. Together they let you drive omp coding-agent sessions running in Stencil Tern from inside the game.

## Key findings

1. **Screen capture is not needed.** ForeverPlusPlus moves game → PC data through `C_AddOns.SaveAddOns()`. Its 256 one-bit helper addons are written to the character's `AddOns.txt` at once [3P-LIVE, build 70862]. That removes the pixel strip and every capture, permission and compositor problem. PC → game uses load-on-demand slot addons and pre-created sound-file signals. All three channels are undocumented client behaviour and can break in any patch (§1, §5).
2. **The font-width channel is reported not working on live Forever.** ForeverPlusPlus says fonts written after launch never load (build 70862, [3P-LIVE], https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md). That contradicts wow-forever-codex's results on beta build 69913. Don't build on it unless an M0 probe shows otherwise (§1.3).
3. **Forever is a Mainline-family client** (Midnight API, secret values, `C_AddOns.*`), not classic-era (§6).
4. **The Tern window plugin API covers the MVP.** `cx.agents` provides `list`, `transcript`, `ask`, `interrupt`, `stop`, `wait` and `start`, and spans remote hosts attached to the window [VERIFIED]. The plugin can **approve and deny omp tool calls** by sending TSP action events to omp's approval surface [VERIFIED]. That is undocumented coupling (§2.4).
5. **Plugin I/O.** The plugin can read and write files, run processes (captured output, no streaming) and make HTTP requests. It cannot listen on a socket. **The companion is a loopback HTTP server, and the plugin short-polls it** (§2.7).
   - In 6+ trials, `tern.fetch` callbacks never fired for responses held ≥200 ms [VERIFIED observation; cause unknown]. My test harness was an in-process Python server inside the eval kernel, so it is not ruled out as the cause. Re-test once against a separate subprocess server in M0.
6. **Use omp's RPC mode only for dictation**, and only optionally. Sessions must stay in Tern (§3).
7. **Hard rules:** no generated input, no automated gameplay, data-only slot files, free and visible source, game state and screenshots opt-in, combat lockdown respected (§5.4).

### 1.2 Game → computer

#### Pixel strips (t3code-wow, wow-ai, wow-forever-codex)

All three draw a grid of solid `SetColorTexture` cells at the top left of `UIParent`, on `TOOLTIP` strata.

**Pixel-exact scaling.** t3code-wow and wow-ai call `SetIgnoreParentScale(true)` and `SetScale(768/physH)` from `GetPhysicalScreenSize()`, so one UI unit equals one physical pixel (`t3code-wow:addon/T3Code/Core/Transport.lua:339-358`, `wow-ai:addon/WoWAI/WoWAI.lua:325-332`). wow-forever-codex uses `SetScale(1/UIParent:GetEffectiveScale())` instead (`Main.lua:71-73`).

**Grid sizes:**

| Repo | Cells per row | Rows | Cell size | Bits per cell |
|---|---|---|---|---|
| t3code-wow | 160 | 40 | 3 px | 3 |
| wow-ai | 200 | 48 | 4 px | 3 |
| wow-forever-codex | 128 | 4 | 4 px | 1 |

Sources: `t3code-wow:Codec.lua:20-24`, `wow-ai:WoWAI.lua:33`, `wow-forever-codex:Main.lua:74-79`.

**Colours.** The 3-bit designs use only pure primaries: R, G and B each fully on or off, thresholded at 128. wow-ai tests decoding with ±120 noise and gamma 0.6–1.8 (`wow-ai:tests/codec_test.js:62-96`). wow-forever-codex rejects mid-grey and strongly coloured pixels (`protocol.py:44-46`).

**Framing:**

| Repo | Frame layout | Checksum | Sequence |
|---|---|---|---|
| t3code-wow | magic `T3`, version, 16-bit seq, length, payload | Fletcher-16 | 16-bit (`Codec.lua:3-5`) |
| wow-ai | magic `C7 1A`, 16-bit id, length, payload | Fletcher-16 | 16-bit id (`Codec.lua:3-5`) |
| wow-forever-codex | 64-byte packets: `CPB1` prompt, `CPBN` control | Adler-32 | not described (`protocol.py:6-20`) |

**Acks:**

- t3code-wow acks inside the next slot snapshot (`Transport.lua:271-289`).
- wow-ai acks by flipping `ack/NNN.wav` (`WoWAI.lua:835-839`).
- wow-forever-codex has no ack. It re-broadcasts the last 8 prompts and dedupes on the PC side (`Main.lua:93-96`).

**Encryption.** Only t3code-wow encrypts.

- It derives keys from a 32-byte master key with `HMAC-SHA256(master, label)`.
- Frames use ChaCha20 with the block counter starting at 1 and an 8-byte truncated HMAC tag. The nonce is 4 bytes of time, 4 random bytes and a 4-byte counter.
- The keys reach the addon only inside slot files, which never appear on screen. Both primitives are written in pure Lua.
- Sources: `t3code-wow:bridge/src/strip-crypto.js:23-57`, `Transport.lua:72-92`, `Crypto.lua:1-61`.
- The goal is to keep the strip unreadable on streams and recordings (`t3code-wow:docs/ARCHITECTURE.md:42`), not to stop local attackers. The key sits in readable slot files, so this only defeats people watching the screen.

**Capture tools by OS:**

| OS | t3code-wow | wow-ai | wow-forever-codex |
|---|---|---|---|
| Hyprland | Window found through the Hyprland IPC socket (`j/clients`), then `grim -g "x,y WxH" -t ppm -` (`capture.js:51-111,290`) | Unsupported. Wayland is not supported (`INSTALL-LINUX.md:7`). | — |
| X11 | ImageMagick `import -window root -crop` at a fixed origin (`capture.js:293-300`) | `XGetImage` on the root window through ctypes. Window found via `_NET_CLIENT_LIST` and the WM class. Optional `_NET_WM_BYPASS_COMPOSITOR=2` (`capture_x11.py:288-368`). | — |
| macOS | JXA `CGWindowListCopyWindowInfo`, then `screencapture -R … -t bmp` (`capture.js:121-138,228-232`) | `osascript` System Events for bounds, then `screencapture -R` (`capture_mac.py:200-281`) | — |
| Windows | none | PowerShell GDI `CopyFromScreen` and `GetPixel`, with `SetProcessDPIAware` (`capture.ps1:24-45,121`) | `PIL.ImageGrab` every 70 ms, with crop coordinates typed in by hand (`app.py:122-124,285`) |

**Strip location and decoding:**

- t3code-wow brute-forces cell sizes 2–8 and small offsets, and adds 40 px of search on macOS for title bars and the notch (`bridge/src/codec.js:113-138`, `capture.js:260-272`).
- wow-ai searches an 8×8 grid of offsets on X11 and 80 px downward on macOS.
- wow-forever-codex needs a manual crop.

#### Addon-list bits (ForeverPlusPlus): game → PC with no screen capture

- 256 helper addons `FPPAgentBit000-255` each hold one bit. The addon calls `C_AddOns.EnableAddOn` or `DisableAddOn(name, character)` only for the bits that change, then `C_AddOns.SaveAddOns()` (`ForeverPlusPlus_AgentChat/AgentChat.lua:220-233`).
- That call writes `WTF\Account\<acct>\<realm>\<char>\AddOns.txt` immediately (`ForeverPlusPlus:docs/forever-api.md:530`) [3P-LIVE, build 70862, 2026-11-07].
- A frame is 32 bytes: seq 1–255, flags (FIRST, LAST, length), a 28-byte payload, and Fletcher-16 (`ForeverPlusPlus_AgentChat/Lib/AgentLink.lua:1-88`).
- Each frame stays written for `HOLD = 0.1` s (`AgentChat.lua:36`), giving about **280 B/s with no ack**.
- The Go side watches the file with fsnotify plus a 250 ms poll (`agent/internal/wow/watch.go:26,84-95`).
- **This is the single most important prior-art finding for ompcraft.** It removes screen capture, Screen Recording permissions, compositor and portal problems, HDR and gamma issues, and the visible strip.

### 1.3 Computer → game

#### Load-on-demand slot addons (t3code-wow, wow-ai, ForeverPlusPlus)

The PC writes a Lua data file into a pre-created `## LoadOnDemand: 1` addon. The addon then calls `C_AddOns.LoadAddOn(name)`, which reads the file from disk at that moment.

Constraints:

- **Each slot loads once per UI session.** `/reload` resets them all (`t3code-wow:docs/ARCHITECTURE.md:22-25`, `ForeverPlusPlus:docs/forever-api.md:531`) [3P-LIVE 70862: "came back in 51 ms"].
- **Slot folders must exist when the client starts.** Several repos report that new folders need a full client restart (`t3code-wow:AGENTS.md:20`, `ForeverPlusPlus:agent/README.md:22`). warcraft.wiki.gg says `/reload` is enough (https://warcraft.wiki.gg/wiki/AddOn_loading_process). **[UNVERIFIED], the sources conflict.** Design for a full restart.
- **Slot counts.** t3code-wow writes a window of slots around the predicted cursor, up to 1200 slots (`bridge.js:911-939`). wow-ai writes the same snapshot into all 200 (`bridge.js:309-329`). ForeverPlusPlus keeps one offered inbox slot and writes it only when something changed (`AgentChat.lua:11-16`).
- **Data safety.** t3code-wow serialises plain data, so text can never become code (`bridge/src/luaser.js:1-3`).
- **Addon-manager fingerprinting.** t3code-wow makes every slot's TOC and XML byte-identical. Otherwise WowUp/CurseForge fingerprinting produced a real collision with a Minecraft modpack (`slots.js:86-98`).

#### Silent sound-file signals

There are two different mechanisms, and the repos' claims disagree:

1. **Presence probe** (wow-ai, ForeverPlusPlus).
   - The addon calls `PlaySoundFile(path,"Master")`, reads the `willPlay` return, and stops the sound at once (`ForeverPlusPlus_AgentChat/AgentChat.lua:275-281`, `wow-ai:WoWAI.lua:415-430`).
   - ForeverPlusPlus measured these properties on Forever 70862 [3P-LIVE] (`docs/forever-api.md:532`):
     - The result is false while the file is deleted and true within 49 ms of it being created.
     - It works with sound off and while tabbed out.
     - A file created after launch is never found.
     - A 0-byte file counts as present.
     - Once found, a file reads as present until the client restarts.
   - **So each signal file works once per game launch.** It is a 1-bit, one-shot flag, and all signal files must be pre-created while the game is closed.
2. **Playback probe** (t3code-wow).
   - There are 8 bell files, each either a 10 s silent WAV of 441,044 B or empty. The size is deliberately above the 174,762 B `Sound_MaxCacheableSizeInBytes`, so the client re-reads the file on every play (`t3code-wow:slots.js:43-62`, `docs/ARCHITECTURE.md:134-142`).
   - The addon plays the next 4 bells every 0.5 s and checks `C_Sound.IsPlaying(handle)` 0.15 s later (`Transport.lua:461-506`).
   - It ignores `willPlay`, which the repo says is always true on Forever (`AGENTS.md:22`).
   - This gives a **reusable** bell. The ring index is the only state.

**Contradiction.** wow-ai's empty-versus-valid `willPlay` flag conflicts with ForeverPlusPlus's "a 0-byte file counts as there". wow-ai covers this with a login self-test that disables the channel (`WoWAI.lua:629-647`). **[UNVERIFIED]** ompcraft must self-test both mechanisms at login, with a known-present and a known-absent control file (t3code-wow's 03999 and 04000 pattern, `Transport.lua:139-182`).

#### Font-width channel (wow-forever-codex)

**How it works:**

- The companion writes a TTF. Each glyph `U+E000+i` (i = 0..511) has an advance of `(16+v)×16` units at 1024 upem, where v is byte i of a 512-byte packet. Glyph `!` is the calibration for v=0, `"` is v=255, and a trailing `~` cancels bearing effects (`companion/native.py:46-71`).
- The addon calls `FontString:SetFont(path,64)` and retries, because the first assignment returns false. It then calls `GetStringWidth(ch.."~")` for each glyph and maps the width linearly between the calibration glyphs, with ±0.20 tolerance (`addon/CodexPixelBridge/Native.lua:132-159`).
- Each packet carries a 476-byte payload. One font is read per ≥5 s slot, which is ≤95 B/s (`Native.lua:3,39`).

**Why recycling is needed.** The client caches a font path for the life of the process. Files created mid-session are never discovered. The fix is 65,535 pre-created names, hard-linked 512 per file on NTFS, each published by atomic replace before its first read (`docs/font-bank.md`, `docs/font-recycling.md:3-48`, `native.py:81-158`).

**Reported failing on the live client.** ForeverPlusPlus (70862) says `SetFont` "never succeeded with a real font … the program made or filled in after the game started, under a known name or a new one" (`ForeverPlusPlus:docs/forever-api.md:533`, https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/main/docs/forever-api.md) [3P-LIVE, not reproduced by me]. This contradicts wow-forever-codex's beta-build results (69913, `docs/testing.md:32-33`, which also has working 0.4.7 code). One of them may reflect a client change between builds [UNVERIFIED]. Treat the channel as unusable unless an M0 probe on the current build proves otherwise.

#### Other inbound channels

- **SavedVariables.** They are written only on logout or `/reload`. wow-ai and wow-forever-codex use them only as a reload fallback or a counter (`wow-ai:bridge.js:726-731`, `wow-forever-codex:Native.lua:113-129`).
- **Synthesized input.** None in any of the four repos.
  - wow-ai's `--inject` only injects a fake strip message into its own bridge (`tests/inject_test.js:33-70`).
  - The one indirect risk is t3code-wow's dictation path: Omarchy dictation backends "send a paste keystroke" to the focused window, which can be WoW (`t3code-wow:bridge/src/voice.js:112-115`). ompcraft must not do this (§5).

### 1.4 Latency and throughput

| Path | t3code-wow | wow-ai | wow-forever-codex | ForeverPlusPlus |
|---|---|---|---|---|
| Game → PC, stated | capture every 150–700 ms (`bridge.js:320-343`) | capture every 250 ms (`capture.ps1:11`) | strip tick 0.25 s, capture every 70 ms (`Main.lua:105`, `app.py:154`) | 0.1 s per 28-byte frame (`AgentChat.lua:36`) |
| PC → game, stated | 1.2 s measured round trip (`docs/ARCHITECTURE.md:155`); signal poll 0.5 s plus 0.15 s | addon tick 2 s; first poll 5 s without signals (`WoWAI.lua:35-37`) | first font 6 s, then 5 s per slot (`Native.lua:3,39`) | signal checked every 0.1 s with the window open, 0.5 s closed; LoadAddOn reply in 51 ms (`AgentChat.lua:37`, `forever-api.md:531`) |
| Bandwidth | strip ≈2.37 KB per frame; slot up to 60 KB | strip ≤3.2 KB; slot ~60 KB | ~80 B/s out, ≤95 B/s in | ~280 B/s out; slot size unbounded in practice |
| Budget | 1200 slots per UI session | 200 per session | 65,535 fonts per bank; no reuse proven within a session | 300 slots per session; about 2000 signals per launch |

[INFERENCE] With ForeverPlusPlus-style channels, a keypress → companion → Tern → result round trip should take about 0.2–0.5 s for an ack: a 0.1 s frame hold, a 0.25 s worst-case watcher, Tern under 0.3 s (§2.5), then a signal check of 0.1 s and LoadAddOn of 0.05 s.

### 1.6 Gamepad (native WoW API)

Only t3code-wow implements gamepad support (`UI/Gamepad.lua`, 853 lines).

- **Input capture.** While the window is open, the main frame calls `EnableGamePadButton(true)` and `EnableGamePadStick(true)`. It handles `OnGamePadButtonDown/Up/Stick` and returns false to consume the press. `PADFORWARD`, `PADSYSTEM` and `PADSOCIAL` pass through (`:26,496-611`).
- **Mapping:**

  | Input | Action |
  |---|---|
  | D-pad / left stick | Move focus |
  | A | Activate |
  | B | Back |
  | X | Read aloud |
  | Y (hold) | Dictate |
  | LB / RB | Switch tabs |
  | Triggers / right stick | Scroll |
  | Back | Sidebar |

- **Focus model.** Its own geometric nearest-neighbour search, plus content-keyed identity for recycled ScrollBox rows (`:48-173,238-438`).
- **Opening from the world.** Hold LT+RT and press Back. The addon polls `C_GamePad.GetDeviceMappedState()` every frame from a frame that never enables gamepad input, because "an addon frame receiving gamepad buttons breaks the LT+RT action bars" (`:743-799`).
- **Not used:** `SetGamePadCursorControl`, `SetPropagateKeyboardInput`, override bindings.
- **Event names.** The real events are `GAME_PAD_ACTIVE_CHANGED`, `GAME_PAD_CONNECTED` and similar. **`GAMEPAD_BUTTON_DOWN` does not exist**, and registering an unknown event throws on Forever (§6).

### 1.7 Dictation

- t3code-wow signals push-to-talk start and stop over the strip.
  - The bridge runs `omarchy-dictation start|stop` and reads the text through `wl-paste --watch` (`bridge/src/voice.js:117-204`).
  - The fallback is `pw-record` + `voxtype transcribe` (`:211-285`).
  - The text returns in the next slot snapshot as `dict` (`bridge.js:525-529`).
  - macOS is "not available yet" (`README.md:56`).
- The other three repos have no dictation.

### 1.8 Clever, fragile, redesign

**Clever, worth re-implementing (clean-room unless MIT-attributed):**

1. The ForeverPlusPlus addon-list bit channel, as the game → PC transport.
2. One offered inbox slot, filled only on change (ForeverPlusPlus), instead of t3code-wow's 80-slot prediction window.
3. A data-only Lua serialiser (t3code-wow `luaser.js`).
4. Byte-identical slot TOC and XML to defeat addon-manager fingerprinting (t3code-wow).
5. Login self-test of the sound channel with a present control and an absent control (t3code-wow, wow-ai).
6. Toasts held during combat (t3code-wow).
7. Tracker anchored *beside* the ObjectiveTracker rather than inside it (t3code-wow).
8. A read-only `GetDeviceMappedState` chord poll to open from the world (t3code-wow).
9. A content-keyed focus model for recycled rows (t3code-wow).
10. A WoW API stub generated from Blizzard's API docs, which errors on unknown widget methods (`t3code-wow:tools/wowstub.lua:130-154`).
11. Lua ↔ host-language codec cross-tests (t3code-wow `crypto.test.js`, ForeverPlusPlus `tests/spec/agentlink.lua`).

**Fragile:**

1. Finite per-session slot budgets, plus a restart to add slots.
2. Undocumented client behaviours: sound-cache size, `PlaySoundFile` presence semantics, LoadAddOn re-reading files. One patch can break any of them.
3. Pixel strips depend on window visibility, exclusive fullscreen, compositor unredirect, HDR, Retina scaling and Screen Recording permission. They also flash in the corner of the screen.
4. The font channel is refuted on live Forever.
5. Bridges bind to private nightly APIs (T3) or one-shot CLIs with no approval path (wow-ai, wow-forever-codex).
6. Dictation that relies on a paste keystroke.

**Redesign rather than copy:**

1. **Drop the pixel strip as the primary path.** Use addon-list bits instead. Keep a strip only as an optional diagnostic if bits ever break [INFERENCE].
2. **Drop the font channel.**
3. **Batch updates.** Spend one slot per *batch*, not per update, and coalesce updates while the window is closed.
4. **Use the Tern agent API as the single backend** (§2), not T3 or CLIs.
5. **Put STT in the companion.** Either omp's own dictation RPC (§3) or whisper.cpp, with no clipboard and no paste.
6. **Design a fresh, versioned wire protocol** with explicit acks (PLAN §4).

## 2. Tern integration

### 2.1 Commands run

- `tern --help` lists, among others:
  - `tern ls|inspect|new|split|run|move|pip|dock|rename|focus|close|kill|wait|keep-open|send|capture|process|events|browser`
  - `tern plugin list|reload|dir|install|remove|link|unlink|types`
  - `tern remote serve|install|login|trust|hosts|discover`
  - `tern web serve`
- `tern plugin --help` says `types DIR` "writes DIR/tern.d.luau for luau-lsp", and `link DIR` uses a package in place.
- The `tern COMMAND --help` pages show that **no CLI verb is agent-aware**:
  - `tern send` sends keys, text or paste to a block.
  - `tern capture` returns screen text.
  - `tern wait` waits for exit, prompt or idle.
  - So a companion that used only the CLI would have to scrape terminals. The plugin API is the right layer.
- `tern plugin dir` returns `~/.config/tern/plugins`. Plugin data goes to `~/.local/state/tern/plugin-data/<id>/` [VERIFIED by the probe].
- The plugin manifest is `plugin.toml`. Its keys are `schema` (integer), `id`, `name`, `version`, `description`, `window`, `host`, `styles`, `blocks`, `lenses` and `match` (strings in the tern binary: `schema must be an integer`, `needs a host or window entry`).
  - The id must be "lowercase letters, digits and -, 1-32 long". This is from the actual error when `id = "ompcraft_probe"` was rejected.

### 2.2 Plugin API map (`tern.d.luau`)

**Two halves:**

- `host.luau` runs in the daemon and `window.luau` runs in the UI (`tern.d.luau:15-16`).
- **`cx.agents` exists only in the window half** (`:791-819`, `:1871-1872`). So ompcraft needs a Tern *window* open on some machine for the plugin to run. The plugin is not daemon-resident.
- Budgets (`:6-13`):
  - 2 s of Lua per call in the host half and 50 ms in the window half.
  - Native calls don't count, but a call may take at most 10× its budget in wall time.
  - Overruns pause the hook for 5 s, doubling up to 5 min.

**Agents** (`AgentsCx`, `:770-819`):

| Call | Semantics (quoted or condensed from the defs) |
|---|---|
| `cx.agents:list()` | "Synchronously lists agent blocks across all sessions". `AgentBlock = {pane, command?, model?, cwd, state: idle\|working\|waiting_input\|exited, last_message?, delivery_error?}` |
| `cx.agents:get(spec)` | Handle with `tocarly(event,"finished",msg)` |
| `cx.agents:start{prompt,cwd,command?,how?}` | Opens an agent block and returns its pane. "Native omp requires TSP send." |
| `cx.agents:ask(agent,text)` | "Synchronously queues/submits one prompt … Native prompts queue until sendable=true" |
| `cx.agents:wait(agent,{timeout})` | Awaitable of the last assistant text when idle (default 30 s) |
| `cx.agents:transcript(agent,{last})` | "Last messages in chronological order (default 50, max 1000) … Reads the omp.session TSP chat, excluding chrome/thinking" |
| `cx.agents:interrupt(agent)` | "Sends Ctrl-C to interrupt the current turn without closing its block" |
| `cx.agents:stop(agent)` | "Closes the agent block and ends its program, without an interactive confirmation" |
| events | `agent_state {pane, old?, new}` and `agent_finished {pane, result: done\|failed\|exited\|closed}`, window only (`:1328-1345`, `:2247-2255`) |

**Other useful surfaces:**

- `cx.session:surface(pane,opts)` returns the live TSP tree (`:1724-1725`).
- `cx.session:event(pane, ev)` "Sends a TSP event such as {ev = "action", id = "main.button", act = "click"}" (`:1728-1730`).
- `cx.session:read`, `cx.session:view` (accessibility tree), and `cx.session:settle`.
- `cx.hosts:list()` lists local and remote machines with state and RTT (`:735-761`).
- `cx.sessions:list()` lists sessions on every attached host.
- `cx:toast`, `cx:pick` and `cx:prompt` are UI (`:1891-1898`).
- `tern.command` and `tern.bind` register palette commands and keybinds (`:2257-2262`).
- `tern.kv` is a JSON store shared by both halves (`:2086-2095`).
- `tern.secrets` stores values in the OS keychain, window only (`:2097-2105`).
- `tern.timer` and `tern.sleep`.

### 2.4 Approvals through Tern [VERIFIED]

I started a throwaway agent in `/tmp/ompcraft-approval-probe` and drove it from the probe:

```lua
cx.agents:start{
  command = "omp --approval-mode always-ask --no-title",
  prompt = "Use the bash tool to run exactly: echo ompcraft-approval-probe …",
}
```

**Results:**

1. **The agent reaches `waiting_input` after about 6.7 s.** `cx.session:surface(pane)` then contains:

   ```
   col  role=omp.editor.ask.approval
     text   role=omp.approval.title  "Allow tool: bash"
     col    role=omp.approval.details  → text "Command: echo ompcraft-approval-probe"
     list   role=omp.approval.choices  items once|session|deny ("Approve", "Approve bash for this session", "Deny")
     button actions.click="deny"    keys [escape]
     button actions.click="approve" keys [ctrl,enter]
     button actions.click="expand"  ("Details")
   ```

2. **Approve works.** `cx.session:event(pane, {ev="action", id="<prefix>.actions/approve", act="approve"})` moved the agent to `working` 0.1 s later. The bash tool then ran (`status: "done"`, output `ompcraft-approval-probe`).
3. **Deny works.** The same call with `act="deny"` on the *current* deny button gave a tool result `"Tool call denied by user: bash"` and the reply `DENIED`.
4. **Node ids are not stable.** The first prompt's subtree was `u.*` and later ones were `18.*` and `1f.*`. An event sent to a **stale** id (`u.actions/deny`) was ignored. About 2.7 s later the call was approved and ran anyway. **[UNVERIFIED] cause.** The pane was visible and focused in the user's window, so a human click is the likely explanation; nothing in the probe sent approve.
   - Rule: re-read the surface immediately before acting, match by `role` (`omp.editor.ask.approval`) and `actions.click`, never by id, and confirm the result in the transcript.
5. **`cx.agents:ask` while an approval is pending does not deny it.** The prompt *queued*, as `ask`'s doc says ("queue until sendable"), and the agent stayed `waiting_input`. This differs from omp's composer behaviour ("Sending a message while calls wait … denies every pending approval", `omp://approval-mode.md:145`).
6. **`cx.agents:interrupt` while an approval is pending denies it.** The tool result was "Tool call denied by user: bash". Then the queued prompt was delivered (reply `STEERED`).
7. **`cx.agents:stop` closed the block**, and `agent_finished {result:"closed"}` fired.

**Caveats:**

- `agents:start` focused a new tab in the user's shown session (`focused: true` in `list()`). Never call it without the user asking.
- The default omp mode is `yolo` (`omp config get tools.approvalMode` → `yolo`; `omp://approval-mode.md:25`). **There are no approvals to route unless the user sets `always-ask`, `always-ask-cached` or `write`, or a tool policy forces a prompt.**

**Answer: yes, a window plugin can approve and deny omp tool calls today** by driving the TSP approval surface. It is an undocumented coupling to omp's surface roles (`omp.editor.ask.approval`, `omp.approval.*`), so pin it with a contract test and a version gate (PLAN §7 risks).

### 2.5 Events and IPC behaviour [VERIFIED]

**`agent_state` events coalesce.** The event log (`/tmp/ompcraft-tern-probe/events.jsonl`) missed transitions. The third prompt's `working → waiting_input → working` produced no `waiting_input` event. The fourth prompt produced only `working (old=waiting_input)`, with no `idle → working` or `→ waiting_input`. The doc says `old` is "Its state at the last look" (`tern.d.luau:1341-1342`). **Use the events as wake-ups and re-read `list()` for the truth.**

**`window_start` does not fire again on `tern plugin reload`.** Only the first link fired it. Kick off loops with a top-level `tern.timer(0, fn)`, whose callback gets a fresh `cx`.

**File-spool IPC works.**

- The companion writes `inbox/<seq>.json`; a 250 ms window-half timer runs it and writes `outbox/<seq>.json`.
- Round trips measured from Python: `[101, 241, 321, 261, 61, 321, 261, 61]` ms.
- Commands: `list` (Lua+native time 14 ms for 20 agents), `start`, `surface`, `event`, `ask`, `interrupt`, `stop`.

**`tern.fetch` to loopback works for immediate responses:**

| Server response delay | Callback fired? | Callback timing |
|---|---|---|
| immediate | Yes (status 200, `has_cx: true`) | 1.1 ms |
| 50 ms | Yes | 51 ms |
| 200 ms, 0.5 s, 1 s, 3 s, 10 s, 12 s | **Never, within the response time + 6 s** | — |

- This held for the callback form, the `:next` form, and a retained awaitable. The server saw the request with `User-Agent: Tern`.
- **[UNVERIFIED] cause.** It might be a Tern bug or a window event-loop behaviour.
- Consequence: **plan on short-polling, not long-polling,** until a newer Tern fixes this. Report it to Stencil.

### 2.6 Remote hosts

- `tern remote serve|install|setup|trust|hosts|discover` puts "the network service in front of session daemons" (`tern remote --help`).
- The window attaches remote daemons as hosts (`cx.hosts:add("user@host:port")`, which verifies the key fingerprint on first contact, `tern.d.luau:748-755`).

### 2.7 Proposed companion ↔ plugin link

Constraints: the plugin can initiate HTTP and touch files but cannot listen. The companion runs on the same machine as the window that hosts the plugin.

| Option | Verdict |
|---|---|
| **A. Loopback HTTP, plugin-initiated short-poll.** The companion listens on `127.0.0.1:<port>`. The plugin `POST /v1/sync` every 250 ms with its outbound events and gets queued commands back **immediately**. | **Choose this.** It is async on the UI thread (fetch is native), works with immediate responses as verified, is authenticated with a bearer token, uses the same JSON for both directions, and is testable with curl. It upgrades to long-poll once fetch delays are fixed (§2.5). |
| B. File spool (verified, 60–320 ms RTT) | Fallback. It is synchronous `tern.fs` on the UI thread, has no auth beyond file permissions, and leaves cleanup races. Keep it as a debug transport. |
| C. `tern.process.run` per message | No. It has no streaming and spawns a process per message on the UI thread. |
| D. Companion uses the `tern` CLI only | No. The CLI has no agent semantics (§2.1). |
| E. Companion as a Tern host-half plugin | No. `cx.agents` is window-only. |

**Token:**

- The companion writes `~/.config/ompcraft/token` with mode 0600.
- The plugin reads it with `tern.fs.read(path, 256)`; `max_bytes` avoids the blocking-FIFO hazard. It caches the token in `tern.secrets` [INFERENCE: same user, same machine].
- Rotate the token on companion restart.

**Leader election:**

- Every window runs the window half (`window_start` "runs once per plugin per window", `tern.d.luau:2254`).
- The companion must accept exactly one leader per `window_key` + epoch and tell the others to idle. Otherwise two windows would both execute `ask`.

**Window requirement:**

- If no Tern window is open on the gaming PC, the bridge is down.
- `tern serve` runs "a headless session on a control endpoint" (`tern help dev`). Whether it hosts window plugins and attaches the daemon is **[UNVERIFIED]**.
- MVP requirement: a Tern window is open, even minimised.

## 3. omp directly (`--mode rpc`)

**What RPC is** (`omp://rpc.md`): `omp --mode rpc` speaks a custom JSONL protocol over the child's stdio, not JSON-RPC 2.0 (`:3-8`).

- It has a ready frame and an optional v2 chunking negotiation (`:37-73`).
- Commands include `prompt`, `steer`, `follow_up`, `abort`, `abort_and_restore_queue`, `get_state`, `get_messages`, `get_entries`, sessions (`new_session`, `switch_session`, `open_session`), and `get_session_lease` (`:125-266`).
- Approvals and other dialogs arrive as `extension_ui_request` (`select` / `confirm` / `input` / `editor` / `ask`) frames, and the host answers them (`:1316-1350`).
- Under `--no-ui`, "tools requiring approval fail closed" (`:1308`).

**Why the companion should not use RPC for sessions:**

- An RPC process owns its *own* session. It is a child of the companion, so it would not appear in Tern as a visible agent block.
- It cannot attach to the interactive omp running in a Tern pane. Sessions are lease-owned: `get_session_lease` / `omp session lease` answer "which sessions a running omp … owns" (`:243`).
- Driving the user's existing Tern sessions therefore has to go through Tern (§2). Sessions started through RPC would be invisible to the user's Tern workflow.

**One justified direct use: dictation.**

- RPC exposes `dictation_start{captureId}` / `dictation_stop → {text}`, with `dictation_state` / `dictation_transcript` / `dictation_end` frames. It uses the user's configured `modelRoles.dictation` and `stt.language`, needs `stt.enabled: true`, and "does not submit a prompt" (`omp://rpc.md:1533-1563`).
- A companion-owned `omp --mode rpc --no-session --no-tools` process could act as a pure speech-to-text engine. It would reuse the user's omp STT setup on both Linux and macOS.
- Today `omp config get stt.enabled` → `false`, so the user would have to opt in.
- Whether `--no-tools` / `--no-session` start fast enough for push-to-talk is **[UNVERIFIED]**.

**Alternative approval path: Collab.**

- Collab hosts publish to a local registry (`omp collab list --json`). Full-control guests "answer host interactive `select` and `editor` requests", which covers approval prompts (`omp://collab.md:72-88,128-138`, `omp://approval-mode.md:37,145`).
- But it needs `collab.autoStart` and the my.omp.sh relay (E2E encrypted, `omp://collab.md:118-126`).
- It is heavier than the Tern surface route, and it is a second control plane. **Not used. Keep it as plan B** if Tern's surface coupling breaks.

**Decision:**

1. The companion talks to omp directly only to run a draft-only dictation engine, in an optional milestone.
2. All session control (list, transcript, send, interrupt, approvals) goes through the Tern plugin.

### 4.1 Does ompcraft need screen capture at all?

**No, not for the core loop.** The addon-list bit channel (§1.2) carries game → PC data through `AddOns.txt`. The channel is identical on Linux (Wine/Proton writes to a host path), macOS and Windows. It needs no capture permission and works on any compositor.

Capture is kept only as:

- (a) a diagnostic or fallback transport if Blizzard breaks `SaveAddOns`;
- (b) an alternative way to attach screenshots. The preferred route is the game's own `Screenshot()` file (§6), which needs no capture API at all.

### 5.2 UI Add-On Development Policy

The original page `http://www.worldofwarcraft.com/policy/ui.html` returns HTTP 404. ### 5.3 Input, multiboxing, pixels, and Midnight/Forever restrictions

- **Input broadcasting.** "We will now additionally prohibit the use of all software and hardware mechanisms to mirror commands to multiple World of Warcraft accounts at the same time, or to automate or streamline multi-boxing in any way." (Kaivax, 2021-05-05, https://us.forums.blizzard.com/en/wow/t/policy-update-for-input-broadcasting-may-2021/956613)
- **Pixel-painting addon plus screen-reading companion.** I found **no Blizzard statement**. The closest test case is a 2026-09-30 forum question about exactly this design for chat translation. It received **no staff ruling**; Vrakthris only linked https://community.developer.battle.net/ (https://us.forums.blizzard.com/en/wow/t/policy-question-is-a-chat-translation-companion-app-allowed/2367458).
  - Community consensus: pixel reading *plus* synthesized input is a bot (§1.C.ii).
- **Blizzard watches pixel channels.** "SetSpriteSheetCell now only accepts secret cell values up to 256. Yeah, we saw that clever scheming going on 😉" (https://warcraft.wiki.gg/wiki/Patch_12.0.0/Planned_API_changes).
- **Blizzard closes communication workarounds.** "Thanks for identifying numerous communication workarounds … We will be locking down all of the APIs mentioned very soon" (same page).
- **Midnight's goal:** "Addons should no longer offer a competitive advantage in WoW combat. They should remain as robust tools for aesthetic customization and personalized presentation of information …" (Ion Hazzikostas, https://news.blizzard.com/en-us/article/24246290/combat-philosophy-and-addon-disarmament-in-midnight).
- **These restrictions apply to Forever** (§6).
- **Forever beta 4 notes:** "SendChatMessage with the "EMOTE" chat type now requires a hardware event when called from addon code outside of instances", and "Trial accounts can no longer send addon messages." (https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes)
- **Precedent for external companions that write addon files.** WeakAuras Companion and the TSM and Wago apps have done it for years with no Blizzard statement for or against (https://github.com/WeakAuras/WeakAuras-Companion).

### 5.4 Hard rules for ompcraft

Each rule is tied to the clause it rests on.

| # | Rule | Rests on |
|---|---|---|
| R1 | **No generated input into the game, ever.** No keystrokes, mouse, gamepad, uinput, xdotool/ydotool/wtype, `SendInput`, CGEvent posting, clipboard-then-paste automation, or focusing the game window. Dictation results land in the addon via the slot channel and the player presses send. | §1.C.ii bots; "one key press = one action" |
| R2 | **No automated gameplay.** Agent output is display-only in game. It never becomes casts, targets, movement, macros, trades, auction actions, or `/run` strings. Approve and deny buttons act on *omp tool calls*, never on the game. | §1.C.ii; Vrakthris AH quote |
| R3 | **No memory reading, process attach, injection, hooks, overlays, or packet capture.** The companion touches only the addon folders it installed, the character's `AddOns.txt`, and screenshots the user asked for. | §1.C.i, §1.C.ii.c, §1.C.viii, §4 |
| R4 | **The addon and companion are free and open source, with no obfuscation.** Encoded *data* is fine when the decoder is in the visible source. | Policy 1, 2 |
| R5 | **Slot files are inert data.** They are parsed by fixed, published addon code. Agent text is never `loadstring`-ed. The serialiser emits only literals. | Policy 2; §1.C.ii.d [INFERENCE] |
| R6 | **No in-game ads, donation asks, or chat transport.** Never send chat, whispers or addon messages for ompcraft. | Policy 3–5; Forever chat restrictions |
| R7 | **Performance budget.** Throttle slot loads and `SaveAddOns`. Do no work on every frame while idle. Back off when the window is closed. | Policy 3 |
| R8 | **Respect combat lockdown and restriction states.** During combat, encounters, M+ or PvP (`InCombatLockdown`, `C_RestrictedActions`), hold toasts, export nothing, and never touch protected frames. Never try to defeat secret values. | §1.C.ii.a; Midnight/Forever statement |
| R9 | **Game state and screenshots are opt-in only.** Default OFF. Toggles are per category. A visible indicator shows while exporting. Only non-secret fields, never other players' chat. Screenshots only through `Screenshot()` and only on explicit player action. Nothing is uploaded except what the player attaches to a prompt. | §1.C.vi; §1.C.v |
| R10 | **One client, one human.** No multibox features. | 2021-05-05 policy |
| R11 | **Fail closed and expect channels to disappear.** Use a kill switch and self-tests. No feature may depend on one undocumented behaviour without a degraded mode. | Policy 8; "locking down … workarounds" |
| R12 | **Disclose risk plainly.** Say ompcraft is unofficial and unapproved, and that no safe harbour exists. Contacting WoWUI@blizzard.com before release was recommended; the owner chose to publish the read-only v0.1.0 without it (2026-11-09). Ask before shipping the uplink (§5.5). | §10.B.ii, §12.C; policy contact line |

## 6. WoW: Forever client facts that drive the design

Source report: Gethe/wow-ui-source `forever` branch at `1.60.1.70862`, plus warcraft.wiki.gg, Blizzard posts, and the ForeverPlusPlus live notes. Every row below carries its tag.

### Identity

**Forever is Mainline-family, not classic-era.** Blizzard's 2026-09-15 WoWUIDev post "An Update On Secrets In WoW: Forever" says: "WoW Forever shares Mainline WoW's UI architecture, including the vast majority of APIs available in 12.1.5 … The addon disarmament changes introduced in Midnight, including secrets, will also be active in Forever." The text is reproduced at https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes [WIKI quoting BLIZ].

- Game type `camelot`, alias `forever`. `WOW_PROJECT_CAMELOT = 18` since build 70170 (`Blizzard_ProjectConstants/Camelot/ProjectConstants.lua`).
- Announced 2026-09-12 (https://worldofwarcraft.blizzard.com/en-us/news/24302093/carve-a-new-path-with-world-of-warcraft-forever).
- Launched 2026-11-04 (https://worldofwarcraft.blizzard.com/en-us/news/24315820/world-of-warcraft-forever-goes-live-globally-november-4).
- TOC `## Interface: 16001` (https://warcraft.wiki.gg/wiki/TOC_format).
- TOC suffix priority: `_Forever.toc` / `_Camelot.toc` beat `_Mainline.toc`, which beats the plain `.toc`.
- Install folder `_forever_`, product `wowf`, exe `Wow.exe` [3P-LIVE, `ForeverPlusPlus:docs/forever-api.md`; no Blizzard page states it].

### Implications

- **APIs are retail-shaped.** Use `C_AddOns.*`; the global `LoadAddOn` / `IsAddOnLoaded` are absent. Classic shims are gone. **Secret values** are active: you cannot compare or concatenate secrets, and chat events become secret during chat lockdown.
- **Opening Blizzard windows from addon code taints** ("attempt to compare a secret number value", `ForeverPlusPlus:docs/forever-api.md:163`) [3P-LIVE]. Let the player open them.
- **Gamepad:**
  - Use `C_GamePad.GetDeviceMappedState()` (no secret flags on the return) or `OnGamePadButtonDown` on a frame that has `EnableGamePadButton` (`IsProtectedFunction=true`).
  - Only the top-most enabled frame receives buttons. `GamePadEnable` defaults to 1 on Forever.
  - Blizzard: XInput only, "beta state", "typing in chat still requires a keyboard" (https://worldofwarcraft.blizzard.com/en-us/news/24316974).
  - `SetGamePadCursorControl` exists but is undocumented, and whether addons may call it is [UNVERIFIED]. Valid `SetVibration` type strings are [UNVERIFIED].
- **Quest tracker.** Mainline `Blizzard_ObjectiveTracker`; there is no `QuestWatchFrame`. Custom modules are Blizzard-internal and taint-prone, so anchor beside the tracker as t3code-wow does.
- **Alerts.** Both are present in the source:
  - `AlertFrame:AddQueuedAlertFrameSubSystem(template, setUp, maxAlerts, maxQueue)` (`Blizzard_FrameXML/Mainline/AlertFrames.lua`).
  - `UIErrorsFrame:AddMessage`, and `RaidWarningUtil.AddMessage`.
- **Screenshots.**
  - `Screenshot()` works, and `SCREENSHOT_SUCCEEDED` has no payload, so pair the file by time.
  - The defaults are `screenshotFormat=jpeg` at quality 3. Locate the folder by watching for the file rather than hard-coding it.
- **SavedVariables** are written on logout, `/reload`, disconnect and quit, not on a crash.
- **Script time and memory caps** are [UNVERIFIED]. `C_AddOnProfiler` exists. Lua errors stop reaching handlers after 100 per session.

## Appendix A — throwaway Tern probe (not shipped)

`/tmp/ompcraft-tern-probe/plugin.toml`:

```toml
schema = 1
id = "ompcraft-probe"
name = "ompcraft probe"
version = "0.0.0"
description = "Throwaway: dumps cx.agents:list() to the plugin data dir"

```

`/tmp/ompcraft-tern-probe/window.luau`, core only. The `fetch` / `fetch_await` spike ops are omitted here; see §2.5.

```lua
local ROOT = "/tmp/ompcraft-tern-probe"
local INBOX, OUTBOX = ROOT .. "/inbox", ROOT .. "/outbox"
local ops = {}
function ops.list(cx) return { hosts = cx.hosts:list(), agents = cx.agents:list() } end
function ops.start(cx, c) return { pane = cx.agents:start({ prompt = c.prompt, cwd = c.cwd, command = c.command, how = c.how or "tab" }) } end
function ops.surface(cx, c) return cx.session:surface(c.pane, { as = "table", nodes = c.nodes or 2000, max_chars = 64000 }) end
function ops.transcript(cx, c) return cx.agents:transcript(c.pane, { last = c.last or 5 }) end
function ops.event(cx, c) cx.session:event(c.pane, c.ev); return { sent = true } end
function ops.ask(cx, c) cx.agents:ask(c.pane, c.text); return { asked = true } end
function ops.interrupt(cx, c) cx.agents:interrupt(c.pane); return { interrupted = true } end
function ops.stop(cx, c) cx.agents:stop(c.pane); return { stopped = true } end

local function poll(cx)
	for _, name in ipairs(tern.fs.list(INBOX)) do
		local path = INBOX .. "/" .. name
		local ok, cmd = pcall(tern.json.decode, tern.fs.read(path, 1048576))
		tern.fs.remove(path)
		local okr, val = pcall(ops[cmd.op], cx, cmd)
		tern.fs.write(OUTBOX .. "/" .. name, tern.json.encode({ op = cmd.op, ok = okr, result = okr and val or nil,
			error = (not okr) and tostring(val) or nil }, true))
	end
	tern.timer(250, poll)
end

if tern.runtime.os == "linux" then
	tern.fs.mkdir(INBOX); tern.fs.mkdir(OUTBOX)
	tern.timer(0, poll) -- window_start does not re-fire on `tern plugin reload`
	tern.on("agent_state", function(ev, cx) --[[ append to events.jsonl ]] end)
	tern.on("agent_finished", function(ev, cx) --[[ append to events.jsonl ]] end)
end
```
